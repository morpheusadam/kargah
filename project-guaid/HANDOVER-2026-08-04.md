## 1. The three architectural pieces everything else sits on

### `post_targets.options` — per-destination structure, not just per-destination copy

`body_override` already existed because the same thought does not fit two networks the same way.
The new nullable JSON `options` column is the same idea one step further: some destinations need
*structure* rather than different prose. A WordPress post has a title, categories, tags, a
draft-or-publish decision and a canonical link, and none of those are copy.

Migration `2026_08_04_000001_add_options_to_post_targets`. `down()` deliberately does **not** drop
the column — a column drop on SQLite rebuilds `post_targets` and fires every `ON DELETE CASCADE`
pointing at it, and `post_targets` is the table the whole retry design rests on.

### `TakesTargetOptions` — a second interface, not a fourth parameter

`Publisher::publish()` is implemented by five classes with no use for options, and PHP will not let
an implementation declare fewer parameters than its interface. So a driver that needs the options
bag implements `TakesTargetOptions::publishWithOptions()` instead, and `PostPublisher` chooses with
`instanceof`. **This is the module's own existing pattern** — `IngestsNotifications` and
`Publishing::ingesterFor()` are the same shape on the read side.

Consequence worth stating: a driver that does *not* implement it never sees the options, even when
a target carries them. A post going to WordPress and to X carries a title for the first, and the
title is not X's business.

### `AttachmentService::publicUrl()` — because Instagram and Threads will not take bytes

🔴 **This decides whether Instagram and Threads work on a given install at all.** Neither accepts
image bytes: the container call takes an `image_url` and **Meta's own servers go and fetch it**. A
picture behind Kargah's `auth` middleware cannot be published to either network by any means.

`publicUrl()` returns a signed, expiring link on `data.file-share` — a route that has always sat
outside `auth` behind `signed` middleware; what was missing was anything that built the URL. Default
window 30 minutes, which is generous by orders of magnitude for a fetch that happens during the call
being made.

`MetaGraph::unreachableInstallReason()` checks the host **before** handing a URL over, because a
`localhost` URL sent to Meta produces a Graph error about a media download failing, which reads as
"Instagram is broken" rather than "this machine is not on the internet".

## 2. The five new destinations

Every one is **pasted credentials**, consistent with the existing five. There is no OAuth handshake
anywhere, and that is a decision rather than an omission: an OAuth callback needs a registered
redirect URI per install, and none of these five requires one to get a working credential by hand.

| Network | Credentials | Driver | Tests |
|---|---|---|---|
| X | `consumer_key`, `consumer_secret`, `access_token`, `access_token_secret` | `XPublisher` + `Support\OAuth1` | `XPublisherTest`, 9 |
| Facebook Page | `page_id`, `page_access_token` | `FacebookPagePublisher` | `MetaPublishersTest`, 11 |
| Instagram | `ig_user_id`, `access_token` | `InstagramPublisher` | (same) |
| Threads | `threads_user_id`, `access_token` | `ThreadsPublisher` | (same) |
| WordPress | `site_url`, `username`, `application_password` | `Modules\Blog\Services\WordPressPublisher` | `BlogModuleTest`, 18 |

The three Meta drivers share `MetaGraph`, a trait holding only what they genuinely have in common:
the pinned version segment (`v23.0`), the error envelope, the container-then-publish dance, and the
signed URL. They do not share a host, a token, or a publishing model.

### The OAuth 1.0a trap, written down because it is the whole task

X's signature base string is built from the OAuth parameters plus any **query-string** parameters —
**never the request body** — whenever the body is not `application/x-www-form-urlencoded`. Both of
Kargah's X requests qualify (JSON tweet, multipart upload). Getting this wrong produces a bare 401
that says nothing. `OAuth1`'s docblock argues it at length and there is a test that publishes two
different tweets at one frozen instant and asserts the two `Authorization` headers are byte-identical.

Also: the query splitter is hand-rolled rather than `parse_str()`, which would rewrite `user.fields`
to `user_fields` and produce a signature X refuses.

### 🔴 What the owner must do by hand — none of this can be done from here

**No CA bundle in `php.ini`**, so no live handshake or verification was possible on this machine.
Every request shape is proved with `Http::fake()` and nothing else.

**X** — developer.x.com → create a project and an app → **User authentication settings → Read and
write** → Keys and tokens → copy API key + secret, then **Generate** access token + secret.
⚠️ If the tokens were generated *before* setting Read and write, they carry the old permission and
must be regenerated. `verify()` still passes with a read-only app (reading `/2/users/me` only needs
Read), so the first *post* is where it fails, with a 403.

**Facebook Page** — developers.facebook.com → Business app → add Facebook Login → Graph API
Explorer → permissions `pages_manage_posts`, `pages_read_engagement`, `pages_show_list` → Generate.
🔴 **What you now hold is a short-lived *user* token — about one hour — and it is wrong twice over.**
Exchange it:
```
GET https://graph.facebook.com/v23.0/oauth/access_token
    ?grant_type=fb_exchange_token&client_id=<APP ID>&client_secret=<APP SECRET>
    &fb_exchange_token=<short-lived user token>
```
then turn it into a Page token:
```
GET https://graph.facebook.com/v23.0/me/accounts?access_token=<long-lived user token>
```
Each entry's `id` is the Page ID and its `access_token` is the Page access token. **A Page token
derived from a long-lived user token does not expire at all** — that is why the exchange cannot be
skipped. If the connect page echoes a *person's* name rather than the Page's, a user token was
pasted.

**Instagram** — same app, same token. The account must be **Business or Creator** and **linked to a
Facebook Page**; a personal account cannot be published to by any API. Add `instagram_basic` and
`instagram_content_publish`, redo the long-lived exchange, then:
```
GET https://graph.facebook.com/v23.0/me/accounts?fields=instagram_business_account&access_token=<long-lived>
```
`instagram_business_account.id` is the account id — not the @handle, not the Page id. The token
field takes the **Page** token.

**Threads** — genuinely different, and reusing the Instagram token is the mistake it invites. Add
**Threads API** as a use case, request `threads_basic` and `threads_content_publish`, and generate
the token on **Threads' own settings screen** — Graph API Explorer does not issue it. Long-lived
exchange is `GET https://graph.threads.net/access_token?grant_type=th_exchange_token&…`.

**WordPress** — sign in as a user with Author or above → **Users → Profile → Application
Passwords** → name it `Kargah` → Add → copy the string (shown once). If the section is missing, the
site is not on HTTPS or a security plugin has switched application passwords off.
⚠️ If a correct password is refused with a 401 that survives regenerating it: Apache running PHP as
CGI/FastCGI drops the `Authorization` header unless `.htaccess` passes it through. That is on the
WordPress side.

## 3. `Modules/Blog`

**The decision, recorded in the `Networks::WORDPRESS` docblock: a WordPress site is a
`social_accounts` row and a published article is a `post_targets` row.** Everything downstream then
works for free — scheduling, the one-minute cron, the atomic claim, the forward-only status, the
per-target error and the media pipeline all apply with no new code, and the composer can send an
article to the blog and a teaser to X as **one intention**. The cost is that "network" now stretches
to cover a website. That is the cheaper of the two wrongs.

`Blog` depends on `Social`; `Social` knows nothing about `Blog`. The driver is registered from
`BlogServiceProvider` through `Publishing::extend()`.

🔴 **`callAfterResolving()`, not `$this->app->resolving()`.** `Publishing` is a singleton, and
`Container::resolve()` returns from `$this->instances[…]` **before** `fireResolvingCallbacks()` — so
a `resolving()` callback registered after the registry's first resolution never runs, and the
symptom is a WordPress target failing with "Kargah has no driver for WordPress" on a machine where
the same code works. There is a test that asks the container rather than constructing the class.

Pages: `/blog` (articles) and `/blog/compose`. Decisions taken and documented at the site of each:
a missing title is derived from the body's first line and the line is **not** then stripped; the
default status is `publish`; `future` is deliberately not accepted (Kargah's cron already owns time);
canonical is an attribution paragraph at the foot of `content` because `<link rel="canonical">` is
stripped by KSES and a meta field needs a plugin; `create_missing_terms` defaults to true and is a
named option because creating a term is a write to somebody else's site.

## 4. The UI audit — what a browser found that the HTTP kernel could not

Every page was walked at **1302px** (44 pages) and at **375px** (24 pages), in a real browser,
measuring layout rather than reading markup.

### 🔴 The page scrolled sideways on every wide page

A flex item's default `min-width` is `auto` — "never shrink below your content's minimum". The board
canvas is a horizontally scrolling strip whose minimum is far wider than the screen, and the whole
page inherited it: at a 1302px viewport the document was **1560px** wide, sidebar, header and footer
included, while the canvas's own scrollbar sat there doing nothing.

Fixed with `min-w-0` on **both** `div.flex.grow` and `.kt-wrapper` in `layouts/app.blade.php`.
**Both, because the chain has two flex items and each independently refuses to shrink** — setting it
on either alone changes nothing at all, which is exactly the sort of half-fix that gets reverted as
"it did not work".

### 🔴 Five popovers on the card back were permanently open

Opening any card showed the start-date, due-date, cover, move and mirror panels stacked on top of
each other and on top of the description. Every one carried `.kt-dropdown` **and** a Tailwind display
utility:

```
.kt-dropdown:not(.open) { display: none }   ← theme, components layer
.flex                   { display: flex }   ← Tailwind, utilities layer
```

**A cascade layer beats specificity outright**, so the panel was `display: flex` whether or not it
was open. Fixed by moving `flex flex-col gap-3` inside the conditional at all five sites in
`⚡card-detail.blade.php`. Written out whole, never concatenated — Tailwind's scanner reads source
text.

This is a new shape of a rule the conventions already had ("pick one mechanism per panel, never
both") and it is worth checking for whenever a `.kt-dropdown` is added.

### Smaller, all fixed

- **`ki-flash` does not exist in the keenicons bundle** — five uses in `⚡butler.blade.php` and
  `⚡card-buttons.blade.php` rendered as blank glyphs, including the *placeholder text* telling
  people to type it. Replaced with `ki-flash-circle`, which does exist and is what the board page
  already used for Butler.
- **`object-cover` was missing from the compiled sheet**, so `⚡publish.blade.php`'s upload
  thumbnails stretched instead of cropping. `kargah.css` rebuilt (71,945 → 73,278 bytes).
- **The mobile menu button had no accessible name** — on *every* page, at every width below `lg`,
  the one control that opens the navigation announced as "button". `title` and `aria-label` added.
- **The board toolbar did not wrap** — five view links plus search, filter, settings and New board
  is ~750px of toolbar against a 360px phone, so `/projects`, `/projects/activity` and
  `/projects/butler` all scrolled sideways. `flex-wrap` added.

### Two things that looked like defects and were not

Recorded so nobody re-investigates them:

- **Unlabelled inline-SVG buttons on the expense pages** — a browser extension injecting into the
  audit iframe. Zero on the real page.
- **`/mail/inbox` email rows reported as having no accessible name** — Chrome's `innerText` returns
  `""` for a `<button>` in that layout while `textContent` is full of subject text. The name is
  there.

### One agent claim that was wrong

An agent reported `bg-mono` missing from the compiled stylesheet. Measured in the browser, it
resolves to a real colour. **Verify every agent report against the running thing** — this is the
third session in a row that rule has earned its place.

## 5. How to verify anything here

```powershell
cd C:\Users\morph\Projects\kargah
C:\Users\morph\PHP\8.3\php.exe artisan test                       # ~9.5 min, 1,126 tests, all green
C:\Users\morph\PHP\8.3\php.exe artisan test --filter=SmokeTest    # ~15 s, every route
C:\Users\morph\PHP\8.3\php.exe artisan test --filter="XPublisherTest|MetaPublishersTest|BlogModuleTest"
```

For a browser pass, `artisan serve` and drive it. **`php artisan serve` is single-threaded**: an
audit that loads pages in a loop will queue behind itself and time out at around a dozen pages.
`PHP_CLI_SERVER_WORKERS` does not work on Windows. Use one fresh iframe per page with a gap between
them, or accept that a screenshot taken during contention may show a stale frame — several did, and
each one cost a wrong conclusion about a card click that was in fact working.

## 6. Open debts

Carried forward, still true:

- `Modules\Core\Contracts\CustomerReader` returns Eloquent models where every sibling returns arrays.
- No per-card deep link — a notification lands on the board, not the card.
- `has:stickers` is the last search operator compiling to "match nothing".
- Butler has no calendar or due-date commands and no if/else branching.
- `/api/v1/customers` is uncursored; card writes and mail sending are absent from the API.

New, from tonight:

- **`v23.0` is a choice, not a verified current version.** Mixpost's own version list confirms
  v23.0 exists and that v25.0 is newer. Check Meta's changelog before the first real post; a retired
  version fails every call with a message naming the version, which is at least loud.
- **Unverified against a first-party source**, because Instagram and Threads are absent from
  Mixpost: `children` sent as a comma-separated string, error code `9007` for "media not ready", and
  the whole Threads surface (`v1.0`, `/threads`, `/threads_publish`, `media_type`, `is_carousel_item`).
  Structurally identical to Instagram's, but memory rather than a read source.
- **The `MEDIA_NOT_READY` retry branch is not under test** — covering it means a real `sleep(2)` in
  the suite. The code is there and reviewable; it is the one thing written and not proven.
- **No permalink for Instagram or Threads.** Both answer with a media id only; a link needs a second
  `?fields=permalink` fetch inside a budget already shared with the post's other targets. The page
  renders an em dash, as it already does for a private Telegram chat.
- **No article edit or detail page in Blog.** An article can be composed and listed; changing one
  means editing the post through Social's queue. Deliberate — editing a target that is already
  `published` is a design question, not a missing form.
- **No `Article` factory or seeder**, so `/blog`'s populated state is not exercised by the demo data.
- **Blog's gallery images are appended as raw `<figure>` HTML.** Correct for classic content;
  a Gutenberg site shows them as one classic block rather than native image blocks.
- **`SocialAccountFactory::connected()` gives every credential the literal `'test-credential'`**,
  which would put that string in the middle of a Graph URL. Harmless today — the new tests build
  their accounts explicitly — but `page_id`, `ig_user_id` and `threads_user_id` want numeric-looking
  defaults before anything relies on it.

## 7. One test assertion was corrected, deliberately

`ProjectViewsTest::test_the_dashboard_view_renders_for_an_empty_board` asserted
`'No lists to count yet'`. The previous session's UI audit split that one message into two — a board
with lists but no cards was being told there were no lists while four named ones sat on the canvas
next door — and did not update the test. The assertion now expects `'No lists on this board yet'`,
which is what an empty board actually says. The behaviour change was right; the assertion was stale.
