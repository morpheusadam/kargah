# Handover — 5 August 2026

The second wave of publishing work: seven more destinations on top of the ten the 4 August
handover describes. Written so the next session starts without re-deriving anything, and so the
owner can connect any of the seven without guessing at a developer portal.

**Branch:** `main`. **Read `HANDOVER-2026-08-04.md` first** — the architecture these seven sit on
(`post_targets.options`, `TakesTargetOptions`, `AttachmentService::publicUrl()`) was built there
and is not re-explained here.

## 1. 🔴 Read this before you trust anything below

**There is no CA bundle in this machine's `php.ini`, so not one of these seven has ever been
called for real.** Every request shape in this wave is proved with `Http::fake()` and nothing else:
the URL, the verb, the headers, the body, and — for the four networks that hide a failure inside a
success — the fact that the driver reads the envelope rather than the status line. No credential
was verified against a live account, no token was exchanged, no post was published anywhere.

That is a real limit on what the tests mean. They prove Kargah sends what its authors believe the
API wants. They cannot prove the API wants it. Where a field name, an endpoint or an error shape
could not be corroborated from a first-party source, the driver's own docblock says so at the site
of the guess — `HashnodePublisher`'s five-tag cap and its list of deliberately-unsent input fields
are the clearest examples, and `Networks::VK`'s pinned `5.199` is another.

**The first real post on each of these seven is the actual test.** Expect the first one to fail and
budget for it. Every driver puts the network's own sentence into `post_targets.error`, so the red
row on the posts page is the diagnostic.

## 2. The seven, at a glance

Credential field names are `Modules/Social/app/Support/Networks.php`'s, which is authoritative —
a driver looks for exactly these keys.

| Destination | Key | Credentials | Copy limit | Pictures | Driver |
|---|---|---|---|---|---|
| Slack | `slack` | `bot_token`, `channel` | 3,000 | 10, fetched | `Social\…\SlackPublisher` |
| Tumblr | `tumblr` | `blog_identifier`, `consumer_key`, `consumer_secret`, `token`, `token_secret` | 10,000 | 10, uploaded | `Social\…\TumblrPublisher` |
| VK | `vk` | `access_token`, `owner_id` | 16,000 | 10, uploaded | `Social\…\VkPublisher` |
| Reddit | `reddit` | `client_id`, `client_secret`, `username`, `password`, `subreddit` | 40,000 | **none** | `Social\…\RedditPublisher` |
| Lemmy | `lemmy` | `instance`, `username`, `password`, `community` | 10,000 | 1, uploaded | `Social\…\LemmyPublisher` |
| DEV.to | `devto` | `api_key` | 100,000 | 1, fetched | `Blog\Services\DevToPublisher` |
| Hashnode | `hashnode` | `api_key`, `publication_id` | 100,000 | 1, fetched | `Blog\Services\HashnodePublisher` |

Two of those limits are Kargah's own rather than the network's, and both are marked as such in the
catalogue: **Tumblr documents no ceiling on a post body** and **Slack's 3,000 is the *block* limit**
rather than `chat.postMessage`'s 40,000 — the moment a picture is attached the message becomes
blocks, so 3,000 is the number that holds in both shapes and therefore the number a live counter
can honestly show. Reddit's 40,000 is the self-post body; its **title is a separate 300-character
field** the driver derives.

"Fetched" in the pictures column is the difference that decides whether an install can use a
network at all. See section 4.

## 3. What the owner must do by hand, and the trap in each

None of this can be done from here. All seven are pasted credentials, consistent with the first
ten: there is no OAuth callback anywhere in Kargah, and none of these seven needs one to produce a
working credential.

### Slack

api.slack.com/apps → create an app → **OAuth & Permissions** → add the `chat:write` **bot** scope →
Install to Workspace → copy the **Bot User OAuth Token**. Then, in Slack itself, open the channel
and type `/invite` followed by the app's name.

⚠️ **Installing an app to a workspace joins it to no channel.** That last step is the one everybody
misses, it happens inside Slack rather than on any settings page, and its symptom is
`not_in_channel` — which the driver translates into a sentence naming `/invite` rather than
printing the raw token, because `not_in_channel` on a red row tells a reader nothing.

The token starts `xoxb-`. One starting `xoxp-` is a *user* token: wider, different, and not what
this wants. `verify()` calls `auth.test`, which proves the token and the workspace and
deliberately does **not** claim the channel was checked — nothing short of posting could.

### Tumblr

tumblr.com/oauth/apps → register an application → use the **API console on that same page** to
generate an OAuth token and secret for the account you are already signed in as. All four strings
are on one screen and there is no callback to configure, which is the only reason this network fits
Kargah's model at all.

The fifth field, `blog_identifier`, is the blog's **host name** — `yourblog.tumblr.com`, or a
custom domain. A whole URL pasted from the address bar is reduced to its host; anything with a path
left in it is refused rather than guessed at, because a path would build a URL that 404s and a 404
from Tumblr reads like the post was rejected.

`verify()` goes one step further than the others here: `/v2/user/info` lists the account's blogs,
so it checks the configured blog is actually one of them. "The four credentials work but that blog
is not yours" is the failure that would otherwise wait until the first real post.

### VK

vk.com/apps?act=manage → create a **standalone** application → obtain a token for it with the
**`wall`, `photos` and `offline`** scopes.

⚠️ **`offline` is the one that matters.** A token granted without it stops working within the day,
and it is byte-for-byte indistinguishable from one that never expires. That is why
`token_lifetime_days` is null for VK rather than a guess: a short-lived token fails loudly on its
first post with VK error code 5, and the driver's message for code 5 names the `offline` scope
rather than leaving somebody comparing two opaque strings.

`owner_id` is your user id for your own wall, or the community id **with a minus sign in front of
it** for a community wall. The minus is the whole of VK's addressing scheme.

### Reddit

reddit.com/prefs/apps → create a **script** app. The short string under the app's name is the app
ID; the secret is next to it. The account must be listed as a developer of that app, and it must
not have two-factor authentication switched on — a password grant has nowhere to put a code.

See section 5 before doing any of this.

### Lemmy

Nothing to register. The instance URL, the account name (or the email it signs in with), the
password, and the community name without its `!`. A community on another server is
`name@instance`, and this instance has to have federated with it already.

⚠️ **Instance version matters and its symptom lies.** Lemmy moved authentication out of the request
body and into `Authorization: Bearer` in **0.19**. This driver sends only the modern shape. An
instance still on 0.18 answers a bearer-only request with a plain `400` carrying
`{"error":"not_logged_in"}`, which reads as a wrong password. If a connection fails that way
against credentials known to be good, check the instance's version before anything else.

### DEV.to

Settings → Extensions → **DEV Community API Keys** → generate one named Kargah. That is the whole
setup; no application to register.

⚠️ **The header is `api-key`, not `Authorization: Bearer …`.** DEV's own documentation names that
header, and a perfectly valid key sent as a bearer token is refused with a 401 that says nothing
about which of the two shapes was wrong. The driver's 401 message says so explicitly, because the
alternative is an afternoon spent regenerating a key that was never the problem.

### Hashnode

hashnode.com/settings/developer → generate a personal access token. The publication ID is the
identifier in your blog dashboard's URL — not the blog's host name.

🔴 **The token goes in `Authorization` raw, with no `Bearer ` prefix**, and getting that wrong does
not produce a 401. Hashnode's API is GraphQL: an unauthenticated request is answered with **HTTP
200** and an error envelope, so nothing about the failure looks like an auth failure until you read
the body. The driver reads the body first for exactly this reason.

## 4. 🔴 Reddit and Lemmy take a real account password

This is the most important thing in this document and it is not being softened.

Every other credential in the catalogue is a scoped, individually revocable thing that a network's
own settings screen hands over: an app password, a bot token, a webhook URL, an OAuth pair.
Revoking one costs the person nothing else. **Neither Reddit nor Lemmy has such a thing.** Reddit's
only flow that needs no registered callback URL is a script app's password grant; Lemmy's API has
exactly one way in and it is `user/login`. So Kargah either stores the account's real password or
does not support these two networks.

It stores it, encrypted like every other credential, and **both connect pages recommend a dedicated
posting account in as many words.** The argument is recorded on the `Networks::REDDIT` constant's
docblock, where the constants are, rather than only in the catalogue copy — because this is the one
decision in the module a future session is most likely to try to design around, and there is
nothing to design around. That is a worse bargain than the rest of this catalogue offers and the
person deserves to be told rather than protected from the choice.

**What Kargah does about it, concretely:**

- The credential bag is encrypted at rest, as every credential already was.
- Neither password ever enters a Livewire property or a log line.
- Both drivers wrap their sign-in path in a `redact()` that replaces the password with
  `[password removed]` in any `PublishFailed` message before it escapes. This is belt and braces
  on purpose: a refusal's detail is whatever the *remote* server's body said,
  `HttpPublisher::detailFrom()` copies up to 300 characters of it into the message, and that
  message is written to `post_targets.error` and rendered on a page. Nothing observed echoes a
  submitted password back — but the cost of being wrong once is a permanent plaintext credential
  in the database, and the cost of the guard is a `str_replace` on a path that only runs when
  something has already failed.
- `CommunityPublisherTest::test_a_password_never_reaches_a_failure_message()` forces both refusals
  to echo the password back, which no real server has a reason to do, and asserts neither reaches
  the message. It is the one test in this wave about a leak rather than about a shape.

Reddit's token is fetched fresh on **every** publish and never stored. Reddit's tokens last an
hour, and an hour-long token in a row a one-minute cron might next read on Thursday is worth
nothing — it would be expired far more often than not, so the driver would need a refresh path
*and* a column to keep it in. Fetching one costs a single request on the publish that needs it.
What is stored is the password, and a password has no expiry to manage.

Two further consequences worth knowing before connecting either:

- **Two-factor must be off** on both accounts. Neither login endpoint has anywhere to put a code.
- 🔴 **Reddit blocks or throttles a generic User-Agent**, and Guzzle's default is about as generic
  as they come. Both Reddit calls — the token fetch as well as the submit — carry
  `Kargah/1.0 (self-hosted freelance workspace)`. If that ever gets dropped from the token call
  only, the failure appears on the *first* request, which is a confusing place to start debugging.
  There is an assertion covering both calls.

## 5. `FetchesOwnMedia` — one host check instead of four copies

`Modules/Social/app/Services/Publishers/FetchesOwnMedia.php`, new in this wave.

Five of the seventeen destinations will not take image bytes and fetch the picture themselves
instead. They are not a family and their reasons differ:

| Destination | Why it fetches |
|---|---|
| Instagram | the container call takes an `image_url`; Meta's servers download it |
| Threads | the same |
| Slack | `files.upload` is retired, and its replacement is three round trips per picture inside one job's budget — so a picture rides as an `image` block pointing at a URL Slack loads |
| DEV.to | `main_image` is a URL; there is no upload endpoint at all |
| Hashnode | `coverImageOptions.coverImageURL` is a URL; its upload endpoint is not in the public API |

Different companies, different reasons, one consequence: **a picture that only exists behind
Kargah's `auth` middleware, on a machine with no public address, cannot reach any of them.**

That judgement had been written out four times — in `MetaGraph`, in `SlackPublisher`, and once in
each of the two Blog drivers — with the same host test copied verbatim into all four. Four copies
of one rule is four chances for it to drift, and the failure it prevents is precisely the confusing
one: a Graph error about a media download failing reads as "Instagram is broken" rather than "this
laptop is not on the internet". The trait is now the single copy, and `MetaGraph` aliases it rather
than keeping its own.

**The judgement is shared; the sentence is not, and that is the point.** The five do not agree on
what to *do* about an unreachable install, so the trait offers a question — `installIsFetchable()` —
and a ready-made sentence for the two that refuse, and each driver decides:

- **Instagram** refuses the post. There is no text-only Instagram post, so there is no request that
  could succeed.
- **Slack** refuses the picture and adds a clause of its own saying the copy alone would have gone
  out. A text-only Slack post is completely unaffected, which is why the guard lives on the media
  path rather than in `unavailableReason()`.
- **DEV.to and Hashnode** drop the cover and publish the article. An article is text and a cover is
  a decoration; refusing to publish eight hundred words over a thumbnail would be Kargah inventing
  a requirement neither network has.

A trait that threw would have made that decision for all five.

What it does **not** do: it cannot prove an install *is* reachable and does not try. A public DNS
name behind a firewall passes here and fails at the far end. It catches loopback, private ranges,
`.local` / `.test` / `.internal` / `.localhost`, and a bare hostname with no dot — the case that is
true on every developer machine — and stays quiet about the case it cannot judge, because a guard
that guessed the other way would refuse posts that would have worked.

**The fix, when it bites, is one line of `.env`:** set `APP_URL` to a public https address. The
sentence the trait produces says so.

## 6. The article destinations, and why that is a different thing

DEV.to and Hashnode live in `Modules/Blog` beside `WordPressPublisher`, not in
`Modules/Social/app/Services/Publishers` beside the other five.

**A social destination takes a string and some pictures.** Everything else about the post is the
network's to decide. That is true of Mastodon, Bluesky, LinkedIn, Telegram, Discord, X, the three
Meta networks, Slack, Tumblr, VK, Reddit and Lemmy — fourteen of the seventeen — even for the two
that need a title, because Reddit and Lemmy have to *invent* one from the body and the composer
never asked for it.

**An article destination takes an article**: a title somebody typed, a markdown body, tags, a
canonical link, a cover, and a draft-or-publish decision. None of that is copy, and none of it fits
`publish(SocialAccount $account, string $body, array $media = [])`.

So both implement `TakesTargetOptions` — the second interface, added in the previous wave — and are
handed `post_targets.options` through `publishWithOptions()`. `PostPublisher` chooses with
`instanceof`. What that buys, concretely:

- **The dependency arrow stays one-way.** Blog may depend on Social; Social may not depend on Blog.
  There is no `Modules\Blog\…` import anywhere under `Modules/Social`, and putting these drivers
  next to the social ones would have meant Social importing Blog's idea of an article the first
  time a driver wanted anything from it. `Publishing::extend()` is what keeps the arrow pointing
  one way, and this wave spent it twice more.
- **The extension point is now proven rather than asserted.** WordPress was the first use, so it
  proved nothing about the shape. DEV.to and Hashnode cost **one line each** in
  `BlogServiceProvider::register()` plus a class. No migration, no change to the scheduler, no
  change to `PostPublisher`, no change to the composer's `optionsFor()`.
- **One options bag, shared by every article destination on a post.** The composer writes a single
  WordPress-shaped bag; each driver takes the keys that mean something on its own network and
  ignores the rest. `categories` reaching DEV.to costs nothing. `BlogDestinationsTest`'s fixture is
  deliberately that full bag, keys and all, so that a `slug` or a `create_missing_terms` breaking a
  DEV.to article would be caught.
- **A driver that does not implement the interface never sees the options**, even when the target
  carries them. A post going to Hashnode and to X carries a title for the first, and the title is
  not X's business.

Three decisions inside those two drivers are worth carrying forward because they are lossy on
purpose:

**DEV.to's four-tag cap drops the fifth rather than failing the post.** Tags must be lowercase
alphanumeric, so each is normalised with `Str::slug($tag, '')`, deduplicated, and cut to four. An
article that goes out with four of its six tags is fixable on DEV in ten seconds; an article that
did not go out because somebody typed a fifth tag into a field shared with WordPress — which has no
such limit — is a publishing tool that refuses to publish. The same argument covers a tag that
normalises to nothing at all, as a Persian or Arabic tag will.

**DEV.to maps WordPress's four statuses onto one boolean, and it errs towards not publishing.**
`publish` is `true`; `draft`, `pending` and `private` are all `false`. A `private` article
therefore arrives on DEV as an unpublished draft, which is not the same thing — DEV has no private
article and a draft is visible to anybody with the URL. It is the closest honest equivalent, and
the alternative of publishing it publicly because there was no private option is the one mistake
here that cannot be undone.

🔴 **Hashnode refuses a non-`publish` status outright rather than publishing it.** `publishPost` is
the only mutation implemented; Hashnode's drafts go through `createDraft` with a different input
type. There were exactly two honest options for an article marked draft: refuse it, or publish it
anyway. Publishing anyway is irreversible and public. So it refuses before any request is made, and
the message names `createDraft` so the reader can tell the limitation is Kargah's rather than their
token's. The composer's status dropdown says so under the field.

One more Hashnode-specific rule, because it is the opposite of every REST driver in this codebase:
**GraphQL refuses the entire document over one unrecognised key.** A REST API ignores a field it
does not know; `PublishPostInput` fails the whole mutation and publishes nothing. So the input is
built from the smallest corroborated set of fields, and `slug`, `subtitle`, `metaTags`, `series`
and `settings` are all believed to be accepted and all deliberately left out. `publishedAt` is left
out for a different reason: Kargah's own cron already holds a post until its time, and handing
Hashnode a future date as well would put two schedulers in charge of one article. That is the same
argument `WordPressPublisher` makes for refusing WordPress's `future` status.

## 7. What was verified, and how

Four suites cover this wave. They are request-shape tests and, as section 1 says, they are the only
evidence that exists.

| Suite | Test methods | What it is for |
|---|---|---|
| `SlackTumblrPublisherTest` | 10 | Slack and Tumblr request shapes, both 200-with-a-failure traps, the Slack fetch guard |
| `CommunityPublisherTest` | 12 | VK, Reddit and Lemmy; the three title rules; the password leak test |
| `BlogDestinationsTest` | 17 | DEV.to and Hashnode; registration from the container; `PostPublisher`'s options branch end to end |
| `NetworkRegistryTest` | 2 | every catalogue entry resolves a driver, and the right one |

```powershell
cd C:\Users\morph\Projects\kargah
C:\Users\morph\PHP\8.3\php.exe artisan test --filter=SlackTumblrPublisherTest
C:\Users\morph\PHP\8.3\php.exe artisan test --filter=CommunityPublisherTest
C:\Users\morph\PHP\8.3\php.exe artisan test --filter=BlogDestinationsTest
C:\Users\morph\PHP\8.3\php.exe artisan test --filter=NetworkRegistryTest
```

⚠️ **The counts above are of test methods read out of the four files, not of a run.** The session
that wrote this document had no shell and could not execute anything, so no pass/fail result and no
assertion total is recorded here. Do not quote a green suite on the strength of this page; run the
four filters and read the last line. The 4 August handover's totals (1,126 tests, 5,411 assertions)
predate this wave and have not been re-measured.

Every suite runs under `Http::preventStrayRequests()`, which on a machine with no CA bundle is the
difference between a failing assertion and `cURL error 60`. Two of them freeze the clock
(`Carbon::setTestNow`) because a signed attachment URL carries its expiry inside the signature:
asserting Slack was handed exactly the URL `AttachmentService::publicUrl()` builds only holds if
both are built at the same instant.

**The property that got the most attention is the same one on four networks.** Slack answers `200`
with `{"ok": false}`; Tumblr answers `200` with a failing `meta.status`; VK answers `200` with an
`error` object; Hashnode answers `200` with a top-level `errors` array. Telegram and the Meta
family already had their own costumes of it. A driver that trusted `$response->failed()` would mark
the target delivered and record a remote id of nothing, so each of those four envelopes has a test
of its own that asserts the *refusal* rather than the success. The rule that falls out of six
instances is worth stating once: **read the envelope, never the status.**

Two other assertions are load-bearing and not obvious:

- **The derived title is copied out of the body, never moved.** Reddit, Lemmy, DEV.to and Hashnode
  all need a title the social composer has no field for. Each takes the body's first non-empty
  line and **leaves it in the body**. Both title tests assert the sent body is byte-for-byte what
  was handed in, because the tempting version of this feature — strip the line so it does not
  appear twice — is silent data loss the person cannot see from Kargah at all. A post that reads
  its first line twice is visible and fixable in thirty seconds. `WordPressPublisher` decided this
  first and it is now the house rule in four more places.
- **Registration is asserted from the container, never by construction.** `new DevToPublisher`
  proves the class exists and nothing about whether a DEV.to target would ever reach it. See the
  next section.

## 8. The two regression tests, and the bugs they were written after

### `tests/Feature/NetworkRegistryTest.php` — new this wave

**The invariant:** every key in `Networks::all()` resolves a driver from `Publishing`, and that
driver answers for the network it was registered under.

**The bug it locks down:** adding a destination is three edits in three files — an entry in
`Networks`, a class in a `Publishers` directory, and a line in a service provider — and the third
is the one that gets forgotten, because the first two are the interesting work. **Forgetting it
produces no error anywhere.** The connect page draws the network from the catalogue, the composer
offers it, somebody pastes a credential, and the failure arrives later on a `post_targets` row
reading *"Kargah has no driver for Slack, so the post was not sent."* That sentence is
`PostPublisher` doing exactly the right thing with a registry missing a line, and it is the only
warning an install ever gets — after the post did not go out.

The second test covers the other half of the same mistake and it is the worse one: a copy-pasted
registration line binding the wrong class. The network has *a* driver, so the first check passes,
and the post goes out — to somewhere else. Every publisher already declares its own key, so the
test simply asks each one who it is.

Seven destinations arrived in one wave with fourteen chances to make that mistake, which is why
this test exists now rather than earlier.

### `tests/Feature/DropdownVisibilityTest.php` — from the previous session

**The invariant:** no `.kt-dropdown` panel in any Blade file, in the app or in any module, carries
a display utility outside a Blade conditional.

**The bug it was written after** is section 4 of the 4 August handover. The theme hides a closed
dropdown with `.kt-dropdown:not(.open) { display: none }` in the **components** layer; Tailwind's
`.flex` lives in the **utilities** layer; and a cascade layer beats specificity outright. So a
panel written as `class="kt-dropdown … flex flex-col gap-3 {{ $open ? 'open' : '' }}"` is
`display: flex` whether or not it is open, for ever, with nothing in the page, the console or the
suite to say so. That shipped: all five popovers on the card back — start date, due date, cover,
move and mirror — were permanently visible, stacked on each other and on the description, from the
moment a card was opened. It looked like the controls had been rendered twice, which is the wrong
diagnosis, and it survived a UI audit that read markup instead of measuring a browser.

The test is a grep with a reason attached. It strips every `{{ … }}` expression from a class
attribute containing `kt-dropdown` and then judges only what is left unconditionally — so a
correctly written `{{ $open ? 'open flex flex-col gap-3' : '' }}` passes and the shipped shape
fails. It lists only the utilities that set `display`; `items-center` and `gap-3` are harmless on a
hidden element and listing them would make the test noisy about markup that is fine.

If a panel genuinely needs an unconditional display utility, the honest move is to stop using
`.kt-dropdown` for it and hide it with `@if` instead — `docs/frontend-conventions.md`, "pick one
mechanism per panel, never both".

## 9. Open debts

Carried forward from 4 August and still true: the `CustomerReader` return-type inconsistency, no
per-card deep link, `has:stickers`, Butler's missing calendar and branching, the uncursored
`/api/v1/customers`, `v23.0` being a choice rather than a verified current version, no permalink
for Instagram or Threads, no article edit page in Blog, no `Article` factory or seeder, and
`SocialAccountFactory::connected()`'s literal `'test-credential'`.

New, from this wave:

- 🔴 **Three catalogue entries are registered from a different module than the one that lists
  them.** WordPress, DEV.to and Hashnode have their entries in Social's `Networks` and their
  drivers registered by `BlogServiceProvider`. With `Blog` switched off in `modules_statuses.json`,
  Social's catalogue would still offer three destinations nothing can send to — the connect page
  would draw them, the composer would offer them, and the failure would arrive on a target row.
  Nobody has switched it off (`modules_statuses.json` has all eight true), so nothing has gone
  wrong. The day somebody does, the catalogue needs to learn which module owns an entry, and
  `NetworkRegistryTest` is the thing that will say so. Its own docblock names this debt.
- **The article composer warns about pictures rather than blocking them, and the three article
  destinations disagree by a factor of ten.** WordPress uploads bytes to its own media library and
  takes ten; DEV.to and Hashnode have no upload endpoint at all and take one cover each. Attach two
  pictures to an article going to all three and WordPress publishes while the other two fail at
  send time with "it takes at most 1 image and this post has 2" — which is
  `HttpPublisher::acceptableMedia()` doing exactly the right thing far too late to be useful.
  `mediaProblems()` in `Modules/Blog/resources/views/components/⚡compose.blade.php` now says it
  under the picker, while somebody is attaching. **Deliberately a warning and not a block**,
  because the person may well mean it: the article gets its cover, the extras reach WordPress, and
  nothing is dropped without having been named first. If that turns out to be the wrong trade, the
  change is in that one method.
- **Reddit takes no pictures at all.** `max_count` is zero in the catalogue on purpose. An image
  submission is a lease upload against Reddit's own media host followed by a submit that references
  the resulting asset, with its own failure modes, and half of it working is worse than none of it.
  The driver refuses a picture before a token is even fetched, with a sentence rather than an
  arithmetic complaint about a maximum of zero. Text posts work; pictures are honest future work.
- **Slack has no permalink.** `chat.postMessage` answers with `ts` and `channel`, and the workspace
  host — the one part a link needs — is not in that response. Learning it costs a second call on
  every publish (`auth.test` returns a `url`, `chat.getPermalink` returns the link outright), spent
  on a courtesy, inside a budget already shared with the post's other targets. The posts page
  renders an em dash, as it already does for Instagram, Threads and a private Telegram chat.
- **Tumblr uses the legacy post endpoint, not Neue Post Format.** `/v2/blog/{id}/post` with
  `type=text` or `type=photo`, because NPF's media upload is a multipart envelope whose first part
  is a JSON document referring to the remaining parts by identifier — two encodings that have to
  agree with each other. Legacy is still accepted and still creates ordinary posts. When Tumblr
  retires it, the fix is one method and the field names in it.
- **`MEDIA_NOT_READY` is still the one branch written and not proven**, unchanged from last wave:
  covering it means a real `sleep(2)` in the suite.
- **Uncorroborated from a first-party source in this wave**, each named at the site of the guess:
  Hashnode's five-tag maximum; the `Str::slug()` derivation of a Hashnode tag slug (if Hashnode's
  own slug differs, the mutation either creates a new tag or is refused with "tag not found");
  every `PublishPostInput` field deliberately not sent; VK's pinned API version `5.199`; and the
  exact wording of several error codes translated into sentences. A named guess is useful; an
  unnamed one is a trap.

## 10. Notes for whoever reads the code next

Three things noticed while writing this that are not defects in behaviour but will mislead a
reader, and one that may be a defect. None of them was changed here — this document's author owned
only this file.

1. **`DevToPublisher` and `HashnodePublisher` still say the host guard is "copied rather than
   shared".** Both class docblocks argue at length that the check is a deliberate copy of
   `MetaGraph::unreachableInstallReason()` and that "if a third destination ever needs it, it wants
   extracting into a small trait of its own rather than a third copy". That extraction has
   happened — both classes `use FetchesOwnMedia` — so the paragraphs now describe a state of the
   code that no longer exists. `MetaGraph` and `SlackPublisher` were both updated to point at the
   trait; these two were not.
2. **`NetworkRegistryTest`'s docblock says "Four of the seventeen" and then names three.** It is
   three: WordPress, DEV.to and Hashnode.
3. **`spec/09-destinations.md` says "The five in bold arrived on 4 August 2026" and seven entries
   are bold.** The table itself is correct and totals seventeen.
4. **VK's `owner_id` normalisation strips a `club` or `public` prefix down to a positive number.**
   `owner()` keeps only a leading minus and the digits, so `club87654321` — which is exactly what a
   VK community URL looks like — becomes `87654321`, a *personal* wall id, and `from_group` is then
   omitted because there is no minus sign. The docblock says those spellings would otherwise "be
   sent verbatim and refused as a malformed parameter", which is true, but the normalised result is
   the wrong wall rather than a refusal. In practice VK answers error 214 and the driver's message
   for 214 talks about the `wall` scope and community administration, which sends the reader
   somewhere unhelpful. Treating a `club`/`public` prefix as negative would be a two-line change in
   `VkPublisher::owner()`.
